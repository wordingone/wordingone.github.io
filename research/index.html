Directions

  1. Credit assignment. Which parts of a model should change after an experience.
  2. Learning only from verified experience. A model grows only by experience that passes verification. Ember built a form of this.
  3. A developmental environment. An external world an agent lives in and learns from, of which benchmarks are verifiable slices. Not an internal world model.
  4. Adaptive learning-compute allocation. Predicting which parameter blocks are worth updating before computing gradients.

01 June–October 2026

Ember

Can one person with one consumer graphics card train a language model from scratch, with no borrowed weights, teacher models or judge models, and keep only the training that passes a check?

Ember

June–October 2026. Code · Research log

The project, in its README's words: “build an AI model from scratch on one home computer with one consumer graphics card”, an RTX 4090-class 24 GB card. The target is a sparse decoder for text, images and audio with a minimum of three billion parameters; that is a goal, not a measurement. Only text (and some image-text) training has run.

Ember is the “learn only from verified experience” direction built and run: training happens in hour-long steps, and each hour's checkpoint is kept only if it passes a recorded check. The idea is close to existing work; no novelty is claimed.

What was built

The gated training loop. A rejected checkpoint is not kept and adds nothing to the chain; the rule is in code.

A research log in which every hypothesis must carry a pass/fail criterion written before the run, with an index of 1,022 run records.

ember-cli, the terminal tool used to run and watch training. A branch, not merged or released, adds a mode that runs third-party open-weights models on one GPU.

What was measured

Training kept across the chain: about 6.06 billion token positions over 1.48 million steps, 33 hourly checkpoints deep, with a check that each hour is counted once.

Benchmarks were run only on an early checkpoint trained on 51,200 tokens, which is not a trained model, and were at chance: ARC-Challenge 0.2295 and HellaSwag 0.2588 (chance 0.25). No benchmark of the kept chain is published.

A measurement that was wrong

A profiling probe reported about 1.76 s per training step. Training actually ran with CUDA graph capture at about 0.19 s, and the probe had never called capture, so 76 of 142 records described a step that training never took. The probe was replaced by one that stops instead of reporting when capture did not happen.

A data decision

An audit found that the largest prose source, FineWeb-Edu (about 29% of corpus bytes), had been selected by a classifier trained on Llama-3-70B-Instruct annotations: an outside model's influence on the data. It was dropped. Whether the current corpus is clean is not established.

What is open

The main goal was not reached: “No current checkpoint is an Ember model”, and the latest candidate is not accepted.

02 March–June 2026 · Concluded

The Search

“Can a system improve itself by criteria it generates?” A falsification study: more than 1,000 experiments. In its first era, no learned action selection beat random actions.

The Search

March–June 2026. Concluded. Code · Manuscript (unpublished, not peer reviewed)

One question, asked of a long run of learner designs: can a system improve itself by criteria it generates? It is a direct form of the question of how intelligence develops. The first era used ARC-AGI-3 game environments and MBPP; the second used ARC-AGI-1 program synthesis. Every design was judged against a written set of six constraints, amended once mid-study (May 2026).

What was built

“1000+ experiments across 14 architecture families”, with scripts and logs, and a manuscript.

What was found

In the first era, no learned action selection beat random actions.

The best designs, which met only part of the constraint set, scored about 1e-5 to 1e-4 depending on the game draw; the draw mattered more than the architecture.

Transfer was zero: a paired test over 100 fixed draws gave 0 wins, 0 losses, 100 ties (p = 1.0).

In the second era the search reached 10 of 200 held-out ARC-AGI-1 tasks; 185 of the 200 runs ended because the search budget ran out.

What is open

The paper's conclusion: whether any design satisfies all six constraints “remains open”. An earlier claim that one constraint was “solved by composition” is marked superseded: that test measured a change in representation, not a gain in task performance. The experiments were not reviewed by independent humans.

03 April–June 2026

WEB-CAD

A CAD workbench that “runs entirely in the browser: no server, no API key, no install”, where a small language model turns a prompt into geometry you can keep editing.

Live demo

WEB-CAD

April–June 2026. Live demo · Code

An experimental workbench, “not a production replacement for Rhino, Revit, or ArchiCAD”. It grew out of gemma-architect, an entry to the Gemma 4 Good Hackathon whose bundled demos are answered from a 60-row prompt cache, not generated live.

What was built

An in-browser agent using Gemma 4 E4B-it through Transformers.js and WebGPU; NURBS surfaces with IFC4 export; a C++ geometry kernel compiled to WebAssembly (booleans, fillet, chamfer, loft); and an MCP server that lets coding agents drive the geometry tools.

What was measured

The C++ kernel against OpenCASCADE: 7 of 7 box/box boolean cases matched in volume within 0.1%, and 60 of 60 robustness fuzz cases ran without a crash. Only box/box booleans were tested; the NURBS check was skipped.

In-browser decoding ran at a median 2.13 tokens per second (range 1.96–2.23, 25 prompts, WebGPU, on the gemma-architect deployment); the file does not record the hardware.

What is open

The README lists “AI agent accuracy varies” among its known limits, and the AI needs WebGPU. At about 2 tokens per second the live model is slow.

04 November 2026 · In progress

Reading a model from its weights

Can you tell what an attention head does from its weights alone, without running the model on any input?

The test case is the induction head, a head that finds an earlier copy of the current token and copies what came next. The plan is to score every head from its weights, write down the top five with the pass/fail rule fixed in the same commit, and only then check, first on a small public model whose induction heads are already published.

No code or result is public yet, and no result is claimed. This place will link the committed prediction when it exists.

05 Method

How the work is checked

I set the questions, the pass/fail rules a result must meet, and the review. The method is built to stop a claim from getting ahead of its evidence.

Criteria fixed before the run
Each hypothesis in Ember's log carries a refutation criterion written before any number exists: “a criterion is never amended after the numbers arrive”. The log's export holds 456 supported, 402 refuted and 100 inconclusive results.
Every number traces to a run
A claim counts only if it points to the stored record of a run that actually executed; the research pages are generated from those records and “a validation failure produces no page at all”.
Instruments that fail closed
A measuring tool that cannot confirm what it measured stops instead of reporting, as the replacement for Ember's faulty profiling probe does.
Replace, don't patch
A failed test or tool is replaced by a new, named one with its own fixed criterion; the old one stays in the record.
Corrections beside the claim
When a public claim outruns its evidence, the correction is written next to it: The Search's “solved by composition” line, and gemma-architect's write-up, marked a historical draft.

Limits: fixed criteria stop moving goalposts; they do not make a badly chosen criterion good. None of this work has been peer reviewed.
